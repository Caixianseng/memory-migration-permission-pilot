# 标准边界检测：旧材料错例审计与开放容器原型合同

日期：2026-10-26。范围为已经公开、反复查看的80条开发材料与40条旧保留材料。本文不读取新保留材料，不修改旧原始响应、检测默认值或评分标签，不新增模型调用。这里记录的是开发诊断与下一步实验合同，不是新的独立验收结果。

机器可读的汇总见 [aggregate summary](../benchmarks/boundary_residual_error_development_20261026_summary.json)。该文件只包含汇总、工件哈希和机制范围，不建立逐题答案明细库。

## 1. 可复核结果与覆盖上限

| 已暴露材料 | TP | FP | FN | 精确率 | 召回率 | boundary候选池中的完整gold span |
|---|---:|---:|---:|---:|---:|---:|
| 开发80条 | 57 | 8 | 1 | 87.69% | 98.28% | 57/58 |
| 旧保留40条 | 18 | 2 | 2 | 90.00% | 90.00% | 20/20 |

共有12个错误材料。一个只识别名称后缀的边界错误，在精确位置评分中同时形成1FP和1FN；这不是两个独立漏检。原始候选池在开发材料只覆盖55/58个完整span，标准boundary后覆盖57/58。闭集分类器不能选择池内不存在的完整值；这项限制是当前候选表示与闭合路径下的具体缺口，不是所有未来算法的上限。

旧40条中的两个漏检则已有完整候选。给它们继续补边界不能解释或解决实体身份判断失败。所有材料均已暴露；无论原型在这些材料得到什么结果，都只能算开发回放。

## 2. 12个错误材料的分层证据

以下保留最短诊断片段，不复制完整测试题、答案或评分标签表。

| 错误组 | 材料数与计分 | 诊断片段 | 机制归因 |
|---|---|---|---|
| 中文组织全名只识别后缀 | 开发1条，1FN＋1FP | `客户账户名称：汐岑勘测器材联合社`，结果仅含`联合社` | 完整全名不在boundary池，属于候选边界缺失；尚未发生“从完整候选中选错”的步骤。 |
| 具体名称恰为通用词 | 旧40中1条，1FN | `法定全名〈客户〉` | 完整`客户`已是untyped候选；语境明确把该词用作名称，不能用“客户永远不是实体”的词表解决。 |
| 项目值未赋类型 | 旧40中1条，1FN | `只填入此值：〈盘山索引L6〉` | 完整项目值已是untyped候选；是实体/角色判定缺失。 |
| 字段名称被规则识别为项目名 | 开发2条、旧40中1条，共3FP | `Project reference = …`；`field labelled Project reference as …`；`section headed [Project reference] …` | 三处被误标的均是`reference`，原始method全部为`rules`。不能把重放后的method当作模型来源。 |
| 描述性占位词被当实体 | 开发3条，共3FP | `本地记录为空壳，办理阶段：开放。` | 同一普通词在三个受保护类别策略下被识别为项目、客户或地址，属于实体性/类型错误。 |
| 定义与角色泛称被当名称 | 开发2条、旧40中1条，共3FP | `客户组织指…一类机构`；`customer organization means…`；`dictionary…defines client…` | 这些出现位置没有具体名称。不能因词形相同而与“名称真的叫客户”的材料共用否定规则。 |

10个FP可以拆为：3个规则字段名误报、6个NER实体性误报、1个不完整后缀span。3个FN可以拆为：1个完整候选缺失、2个候选存在但未定类。没有证据支持直接修改材料标注；只标组织后缀所遗漏的独特前缀仍会泄露，不能仅以“严格评分”淡化它。

### 2.1 为什么三个reference并非模型错误

公开旧工件 `context_candidate_detection_20261026_v2.zip/materials.json` 的baseline明确把三处`reference`记录为`method=rules`。源码 [privacy.py](../memory_migration_study/privacy.py#L333) 对`project`后紧邻的一个ASCII单词提出PROJECT发现；该规则使用有限排除词，`reference`不在其中。

标准boundary将核验后的发现重放进公共检测闭合路径，输出method统一成为`agent`。因此，最终method表示这条重放路径，不能直接反推原始模型归因。追溯时应同时核对原始baseline和reconciliation的输入、输出，而不是据最终`method=agent`计算“模型误报率”。

不能为通过门槛增加`reference`停用词：`Project Reference = approved`中Reference也可能确实是项目名。更不能把所有key内的字符串都视为公开内容。

### 2.2 具体代码路径

- [structured_candidates.py:18](../memory_migration_study/structured_candidates.py#L18)使用有限字段别名；[第204行](../memory_migration_study/structured_candidates.py#L204)忽略未知key，[第253行](../memory_migration_study/structured_candidates.py#L253)要求当前片段从已知key匹配。复合键`客户账户名称`不能自动提供全值边界。仅补这个已见键的别名没有独立泛化证据。
- [boundary_reconciliation.py:190](../memory_migration_study/boundary_reconciliation.py#L190)按当前结构证据处理key内发现；[第200行](../memory_migration_study/boundary_reconciliation.py#L200)要求同类别、包含当前typed seed的字段值。现有算法不会凭任意冒号把全文扩成实体。
- [privacy.py:137](../memory_migration_study/privacy.py#L137)的实体闭合只扩展相连ASCII标识字符，不能补出中文组织前缀；[第173行](../memory_migration_study/privacy.py#L173)的传播继承敏感性，不产生授权。
- [ner_detector.py:156](../memory_migration_study/ner_detector.py#L156)将当前受保护类别映射到固定NER标签定义，[第171行](../memory_migration_study/ner_detector.py#L171)校验精确片段和阈值。源策略哈希核验不是任意自然语言策略的语义解释。旧baseline没有保存阈值以下的所有输出，不能据漏检推断内部tokenizer或阈值因果。

## 3. 源生成标签的真实覆盖能力

签名标签与可信语义标签是不同属性。

- [memory_labels.py:143](../memory_migration_study/memory_labels.py#L143)验证findings的位置、类别并绑定源、内容、策略和访问grant；空findings也可能形成有效签名。
- [memory_labels.py:228](../memory_migration_study/memory_labels.py#L228)验证签名、版本、来源与位置绑定，未证明标签实体性或完整性。
- [memory_labels.py:515](../memory_migration_study/memory_labels.py#L515)合并有效正标签，[第535行](../memory_migration_study/memory_labels.py#L535)防止下游边界处理把已签正标签静默移除。它可以增加保护，不能靠一个“非敏感”模型意见撤销原保护。
- [memory_builder.py:118](../memory_migration_study/memory_builder.py#L118)将同一标签文字应用于fact内所有相同文字位置，不能把这种字面传播当成逐位置角色证明。

已有生成Union试验包含一个可核对的真实边界修复：`买方荷岑应用研究联合社接受了修改方案…`，NER标签只含`联合社`，Union标签含完整组织名称。该fact对另一个公开观察机构的额外标注仍然存在。这说明正标签能够修边界，也说明“多标一次”不能自动提高精确率。

该试验8个完整源的哈希与旧120材料中的66种memory全文哈希交集为0。不能把生成试验结果记作本次三个FN的已实测修复。若源写入接口原本提供正确完整的typed span，机制上可以保护这三个值；若标签仍由同类检测器推断，则其漏检、误报和同文角色问题仍需独立验证。

## 4. 下一轮：开放key/value容器原型的精确合同

状态：**仅设计，未实现、未运行、默认关闭。** 建议名称`typed_seeded_open_container_candidates_v1`。它先补齐候选表示，暂不承担自动敏感判断、误报删除或访问授权。

### 4.1 输入与输出

生产输入仅为当前`payload`、`policy`、已有精确`typed_findings`及固定解析配置。不得额外接收gold、case/story ID、评分结果、已见名称词典或模型输出答案。payload内的`source_id`只用于位置与哈希绑定，禁止按其文字分支或推断类型。配置与解析器版本必须进入工件绑定。

输入发现必须是同源、完整位置合法且属于当前受保护类别的typed seed。原型不创造类型，不从key的词义推导类型，不用文本中的owner/ACL声明授权。

输出为闭合字段的`candidates_only`结果，包含：

| 字段 | 约束 |
|---|---|
| `status` | `candidates_only`或`needs_review`，绝不报告完整检测成功 |
| `payload_sha256/policy_sha256/full_policy_sha256/source_sha256/config_sha256` | host重算，禁止信任输入自报哈希 |
| `containers` | 精确key、delimiter、value-container位置；语法类型及完整来源范围 |
| `completions` | 原seed位置、候选完整value位置、同一个继承类别、container引用、证据与原因 |
| `decisions` | 对每个seed记`unchanged`、`proposed_completion`或`needs_review`；不提供删除发现的动作 |
| `errors/complete` | 预算或解析失败不得伪装成空结果成功 |

所有范围都必须与原文切片一致。hash、签名或“这是字段”的文本本身都不是语义或授权依据。候选可供后续独立检查；在另行预注册自动应用规则前，不覆盖最终检测结果。

### 4.2 首版支持范围

只解析**完整物理行上的单个key/value字段**；key不受业务别名表限制。分隔符仅为引号/括号外的一个`:`、`：`或`=`，两侧非空，忽略外围空白。多个外层分隔符、跨行引号、多个字段或截断输入进入review，不择取方便的部分。JSON对象、表格、自然语言的“标题为…其值为…”属于后续能力，首版不得声称支持。

建议固定key最多80字符、value-container最多256字符、每payload最多128个容器；输入总长度沿用现有4096字符上限。超限需完整失败，不能截断、删候选或只保留命中旧题的部分。

只有严格位于value-container内部的已有typed seed才能提出补全。seed位于key、跨越分隔符或跨越容器边界时一律不产生completion，保留原发现。value中存在多个不嵌套typed seed、竞争类别、列表/多值结构或未闭合括号时进入review。

引号、没有空格、JSON字符串或只有中文字符，仅证明词法容器形状，**不证明其中只有一个语义实体**。因此首版允许把一个单值形状的全value加入候选池，但标明`semantic_atomicity=unverified`，不得自动扩大最终敏感范围。若以后接入可信业务schema声明的原子字段，需单列注册、内容绑定与对照；源文本自称“原子字段”不算该证据。

### 4.3 明确不做的操作

- 不因候选在key内就删除、降级或公开它。key可以是人名、客户名、项目名，或带有真实敏感值。
- 不用`reference/customer/client/空壳`等已见词作为停用词，也不匹配已见公司、项目名称或case ID。
- 不从field角色推出“非敏感”；role与sensitivity是独立维度。
- 不新增授权，不改变read/share/export、接收者或恢复门控，不让query文字变成记忆证据。
- 不扩展到任意自然语言语义解析；无法判定时保持原发现并review。

三个reference误报在该首版合同下**明确保留**：完整句子内的`Project reference = …`不属于独立字段行；另两条属于自然语言标题关系。即使以后语法提取出key位置，也不能在未解决敏感key反例前自动删除其中发现。

## 5. 必须先通过的独立反例

这些是新构造的机制测试要求，不是旧答案回填。实现前冻结输入、期望的结构动作与失败条件；独立变化名称、key和排版。

| 测试族 | 示例形状 | 期望 |
|---|---|---|
| 未知key＋后缀seed | 随机复合键`…：<随机组织全名>`，seed仅为末段 | 可产生完整value候选；保持同类别，不默认为已证明的完整实体。 |
| 原值恰为角色词 | 某独立字段的真实值恰为`客户`或`Reference` | 不用词表排除。 |
| 敏感key | `<人名> = approved`；`Project <随机项目名> = approved` | key中的typed seed原样保留，不因是key而删除，不补成approved。 |
| 非实体描述在key | `Project reference = <随机标识>` | 可记录key/value角色；不凭角色删除key中已有发现。 |
| 容器内短句 | `备注：该联合社已同意下周复核`，seed为`联合社` | 不能声称整句是组织名；仅语法候选/待审，不自动扩大最终发现。 |
| 无标点中文多实体 | `说明：甲机构联系乙机构`，含一个或多个seed | 单个seed不证明单实体；多个seed明确review。 |
| 多值与转义 | 一个字段含列表、嵌套键值、未闭合引号或多个外层分隔符 | review且不截取。 |
| 同文不同角色 | 同一文字在key、value、另一个句子分别出现 | completion仅绑定当次位置；不得据文字相同删除或扩大其他位置。 |
| 来源和预算变化 | 源内容变更、篡改位置/hash、超长value、超容器数 | 固定失败；不得保存部分成功冒充完整结果。 |
| 无typed seed | 结构清楚但检测器未识别任何片段 | 不创造敏感类别，不因字段看起来重要而猜测。 |

## 6. 验证顺序与停止条件

1. 先用确定性反例验证位置、分隔符、key/value角色、预算与来源绑定。此阶段无模型，也不测回答正确率。
2. 对旧80/40只报告新增完整候选覆盖、错误扩边候选、review率及原typed发现是否保留。完整候选覆盖增加不等于检测TP增加。
3. 若自动应用需要可信原子schema，先明确这个新增输入条件，独立分组评测；不能偷偷把旧gold变成schema。
4. 只有完成上述机制验证、冻结自动应用条件并取得新独立材料，才能评价检测精确率/召回率与合法回答效用。不得将本次开发回放宣布为通过联合P90/R95验收。

当前优先级是消除可解释的候选表示缺口；实体性、敏感性、授权和回答效用分别保留证据与分母。本文没有主张新算法优势或论文创新已经成立。
