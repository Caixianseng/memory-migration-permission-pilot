# 源端角色证据：编码器预验证协议

日期：2026-10-25。只验证现有模型能否从8个已暴露原始来源提取业务角色对应的精确值，不接入默认流程，不以此替代A→B任务验收。

## 1. 来源、参考与角色语义

输入仅为`examples/privacy_semantics_v1/development/runtime.json`中的8份`source.text`，不得输入查询、原问答评分答案或新角色参考。角色参考由另一Agent依据原文预编，主线程在推理前逐字复核；非独立真人标注，也不算新保留集。

固定7种显式业务角色：customer、buyer、consignee、account_holder、audit_observer、carrier、status。customer要求原文明示客户/client，不因隐私类别CUSTOMER或买方/收货方身份自动推导。账户持有人指具名持有组织，不指当前认证用户；公开角色不赋予公开访问权。注入式便条不作为事实或授权。

参考共20个角色—原文值关系，名称和值以及支持片段均有精确Unicode坐标。参考哈希为`8693b5cd8e682de5eee08783ca623dc57b5329cb19d531d7e8be97a41c2926a2`；任何真实推理前先验证哈希并冻结，全部推理结束后才读取其标签评分。实测前撤回umbrella customer定义、改用显式角色的澄清已记录；原问答gold没有变化。

## 2. 固定API、预算与强基线

沿用已固定的GLiNER2.5多语权重与官方代码、CJK分词、阈值0.5。采用显式`mode='anchorless'`结构schema和7个固定独立角色字段，通过原生`model.extract`执行；不是声称已复现JointIE跨字段关系。

这一API选择在实测前确定：官方便利`extract_json`的natural模式会以首字段作anchor，而多数材料没有显式customer，不适合这里的独立角色集合。不能运行后再换schema以提高分数。原始输入及完整schema必须在真实编码入口以`max_len=None`检查，不得超过512；超长保留为失败，不截断、不换字段重跑。

每源最多1次结构抽取、1次默认组织NER，整体最多8+8=16次编码器API调用；不使用Qwen、云端或新增模型下载。神经前向/实际抽取调用另行计量，不将API次数冒充独立样本。

完整简单基线为默认组织NER候选加原文明示角色邻近/结构字段规则。规则表与边界须在实测前冻结，不硬编码公司名或参考值；若基线与模型同样好或更好，不宣称模型新算法收益。状态字段规则的推理与新增编码器成本分别记录。

## 3. 输出与验收

保留完整原生raw响应及confidence、start/end和quote；宿主逐字核对`source[start:end] == quote`。缺少原生坐标不能通过第一次字符串匹配补齐，多次出现的同字符串保留各自明确坐标。格式、类型、偏移或原文不符不能静默转成成功空结果。

按完整`(source_id, role, start, end)`集合计精确率与召回率，另列值跨度正确但角色错误、边界不完整、缺失、额外候选、重复及源级待审。不存在某角色是允许的，不能为凑齐7字段编值。原文支持与角色语义正确分开；仅有字面片段不证明角色关系成立。

默认敏感标注和授权不改。未来即使加入角色卡，也须绑定源内容、值及支持片段；只有二者均落在获准exact-fact范围内才可转交。模型声称“公开观察方”不能降级已有保护，角色类型也不能成为授权依据。

这是一轮可否继续的开发预验证。结果不足就保留负结果，不扩展新生产组件；结果有用才设计同候选池、同预算、带/不带角色证据的完整下游对照。原120条检测、64题新保留集、云端协议、原生稳定性与创新审查继续单独保持未完成状态。
