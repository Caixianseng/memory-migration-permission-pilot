# 敏感类别合同一致性审查

日期：2026-10-27。结论来自静态源码、既有合同/测试与已暴露80/40代表输入；新增模型调用、前向、原生客户端和付费调用均为0。未读取fresh64，未改生产代码、旧gold或原始结果。机器摘要见[detector_category_contract_20261027_summary.json](../benchmarks/detector_category_contract_20261027_summary.json)。

**当前同一个`CUSTOMER`键承载两种不同语义；完整policy哈希批准不能把它们变成同一个识别任务。** 这影响未来共同验收与部分方法间排名解释，不推翻已批准宽口径/保守遮蔽合同下的旧结果。

## 1. 两种合法policy必须分开

| 预定义policy | 所需证据 | 边界 |
|---|---|---|
| 客户关系组织 | 具体组织名，并有可见证据表明其在指定业务范围内是客户、买方或接收方 | 单纯出现一家组织不够；组织类型阳性不能证明客户关系。历史/当前关系是否均保护也应预定义。 |
| 任意具体组织 | 当前位置是某个具体组织的完整名称；无需客户关系 | 普通角色词、类别定义与状态词不因词形而成为名字；组织名恰为普通词时仍可成立。 |

二者都可以成为合法隐私policy。当前GLiNER适配器的固定标签合同明确对应第二种；若在第一种policy下使用它，只能称已授权的保守组织遮蔽近似，并单列额外遮蔽。当前本地Qwen提取prompt的文字则意图对应第一种；这不等于已经证明模型能正确推断客户关系。

## 4. 旧80/40的代表残差是否依赖隐藏答案

| 代表输入 | 只凭已声明合同和可见文本的结论 |
|---|---|
| PROJECT：标题为【项目代号】，只填入此值〈盘山索引L6〉 | 类别与值边界可见，完整候选存在。该FN不能用隐藏标签或题意不清解释，也不能靠继续补边界解决。 |
| CUSTOMER：一家组织，法定全名〈客户〉，后面的角色栏目为空 | 足以认定组织专名，无法认定客户关系。对既有宽organization合同，旧gold成立；对严格客户policy，需另外的关系证据。字面CUSTOMER键本身没有把二者区别传给接入者。 |
| 3个描述性FP：memory为“本地记录为空壳，办理阶段：开放” | 该位置没有实体命名；query中另有真实私有字段不使memory内状态成为实体。负标签可判。 |
| 3个定义/角色FP：客户组织指一类机构、customer organization means…、dictionary defines client… | 均明确为无具体名称的定义，type-policy又排除泛称。负标签可判，不能用无条件“客户不是名字”词表修复。 |

因此当前无依据静默改这批gold；PROJECT的实体类型推断和6个FP的实体性判断仍是识别器问题。〈客户〉在宽组织合同内也是漏检，且必须单列合成边界例。这些判断不需要case ID或评分标签入模，不代表旧120获得了新的独立验收。

## 5. 下一独立评测的最小合同要求

先选上述一种本体并冻结`ontology_id/version`与类别定义字节，分别绑定policy、实际入模prompt/labels/hypotheses、模型与适配器版本以及gold版本；明确不支持或仅保守近似的后端。保留旧结果、旧标签及其已披露合同，不追溯改口径。类别定义是独立可信任务输入，不能来自case ID、答案、已见名称词典或payload自称的权限。

随后仅作一项明确的审查：同一可见文本“某具体组织，未提供客户关系”在宽组织policy与严格客户policy下应形成不同的预期判定；泛称/真正登记名继续按位置分开。完成共同本体/提示绑定后，才在新的独立材料比较检测P/R与额外遮蔽。无需为了此次合同发现重跑旧120、增加模型臂、调阈值或扩大到全项目。

本报告不实现本体重构，不宣称修复、性能提升或安全保证；它只确认一个有边界的语义合同不一致与下一轮先决条件。
