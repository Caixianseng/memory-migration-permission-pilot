# NLI候选语义：冻结合同与强基线

日期：2026-10-26。定位是**标准NLI候选分类基线**，不是新算法或权限层。本文为运行前设计核对；本轮未读取old120 gold或fresh64，未执行模型或原生调用，也未改默认检测、源授权或认证标签链。

机器合同：[nli_candidate_contract_v1_20261026.json](proposals/nli_candidate_contract_v1_20261026.json)，SHA256 `7eae94ddf1e0995e36fa3d6f0303673ad2551496a6c4c51e0bb99d9560a9a29b`。具体模板、规则优先级与模型revision以该文件为准，实现与运行计划应绑定其原始字节。

## 1. 输入、策略与位置

沿用现有`_sources/_policy`、位置绑定候选池以及`compose_gliclass_detection`的保护分层。host先核验payload/policy/pool/source哈希、类别范围和原文`source[start:end] == quote`；start/end是未修改原文的Python字符区间。每候选只输入其所在的一份**完整原始source**，在精确位置插入`[[TARGET]]`和`[[/TARGET]]`，前加固定`Text:\n`。标记或模型保留token冲突即阻断，不另换标记、删文或截断。

CID、source ID、NER建议类别、registry值及评分字段不额外进入模型。query与memory分别处理；query中的实体可以成为query本身的待遮蔽跨度，但不能变成memory事实、来源证据或权限。所有原文仅在本地NLI中处理。

只支持运行前独立批准的type-policy。host按`protected_categories ∩ {PERSON, ADDRESS, CUSTOMER, PROJECT}`生成类别断言，顺序固定；不是把任意业务指令交给NLI解释。当前CUSTOMER沿用既有“customer or organization name”桶，不等于证明某组织与另一主体有客户关系。若未来收窄到“必须有客户关系”，需独立版本与新评测，不能悄改旧真值。

## 2. 单套英文hypothesis

中文只供解释，**不执行第二语言推理**。

| 键 | 唯一实际英文hypothesis | 中文说明 |
|---|---|---|
| value | In this text, the marked occurrence is a specific entity value. | 该位置是具体实体值 |
| field_label | In this text, the marked occurrence serves as a field label or heading. | 该位置充当字段名或标题 |
| generic_role | In this text, the marked occurrence refers to an unnamed generic role or a dictionary concept. | 该位置指一般角色或词典概念 |
| PERSON | In this text, the marked occurrence gives the name of a particular person. | 具体人名 |
| ADDRESS | In this text, the marked occurrence gives a particular postal or physical address. | 具体地址 |
| CUSTOMER | In this text, the marked occurrence gives the name of a particular customer or organization. | 具体客户或组织名称 |
| PROJECT | In this text, the marked occurrence gives the name, code, or identifier of a particular project. | 具体项目名或标识 |

每个实际评分CID均执行三个role和该policy允许的所有语义类别，不根据初始分数提前退出。至多七次前向；类别为空时不新增语义保护类别，硬格式/registry保护另行保留。

## 3. 固定分数与最终分支

每对premise/hypothesis独立保留三分类logits，按已资格模型的`entailment=0, neutral=1, contradiction=2`计算稳定softmax。阈值只有固定`tau=0.80`：`pE>=tau`记E，`pC>=tau`记C，否则记U。U包含neutral及置信不足，不是逻辑否定；该分数尚无隐私任务校准保证。禁止先丢neutral、跨hypothesis归一化或强制role/category argmax。

令`E_cats`为允许类别中判为E的集合，分支顺序固定：

```text
if len(E_cats) > 1:
    needs_review
elif len(E_cats) == 1:
    category = its only member
    if value == C:
        needs_review
    elif typed_prior is not null and typed_prior != category:
        needs_review
    else:
        protect(category)
elif all tested categories == C or (value == C and (field_label == E or generic_role == E)):
    nonvalue_under_this_policy
else:
    needs_review
```

所以唯一类别E且value非C时，即使另一类别U，或field/generic为E/U，仍保留该跨度的**敏感finding与后续遮蔽**，不是将原值外发。一个片段可能同时有字段与具体值含义；不能拿标题证据删除明确的类别阳性。typed候选不允许换类别；unknown必须有独立类别断言阳性，只有value阳性或“像名称”不够。

无类别E时，全部类别C表示在本次闭集type-policy内没有合格类别；或valueC与field/genericE共同提供非值证据。允许类别为空的情况显式按“该policy无受保护语义类别”解释，不凭空宣布全局公开。其余状态待审。待审不是合格检测结果，必须留在完整材料分母。

此前“value、field、generic及所有其他类别都须明确C才允许相应决定”的建议**未被采用**。它把独立断言误当严格互斥分类，过于保守；修订依据是合同语义，不是读取gold或比较成绩后的调参。此次规则同样没有理论安全或性能改进保证，效果需按冻结实验报告。

## 4. 不可降低的保护与可变候选

- EMAIL/PHONE/ID/AMOUNT/DATE等四语义实体以外的硬格式finding、registry及已认证标签/注册正保护跨度不可被NLI删除或改类。
- 未认证的PERSON/ADDRESS/CUSTOMER/PROJECT NER与弱规则候选才可按上述决策保留、移除或提升；“不改规则正保护”不能扩大成“任何弱规则输出都不可评估”，否则无法测试误报修正。
- 继续执行原边界与重复闭包，并报告被闭包重新加入的finding；不为提高分数绕过标准保护。当前新阶段不接默认或签名标签链，不重新认证任何数据，不产生或改变read/share/export/委托权限。

独立逻辑核对未发现分支本身扩大源授权或将policy外类别加入闭集：保护只来自允许类别的明确E，typed类别改变受阻，immutable在host组合前后保留。**但NLI可能把真实敏感值错判为非值**，从而让弱候选漏遮；唯一类别E也可能是假阳性。这是待测检测风险，不应被“规则一致”写成隐私安全证明。

## 5. 三臂、预算和强基线

`standard_boundary`是主强基线；同一份baseline和候选池只做一次NLI判定，缓存按模型/合同/完整source/policy/位置绑定。`NLI-only-existing`只消费standard_boundary原候选集合，`NLI-full-pool`还可消费新增候选。两者不分别调提示或阈值。物理前向总数只记一次，另列各臂消费的候选/判定成本，不能把共享cache当独立多轮模型证据。

任何前向前先对整份材料的全部待评分对完成tokenization；完整premise、hypothesis及特殊token必须`<=512`，且`truncation=false`。超长不改窗口、不换模板，整份材料零前向阻断并留分母；执行中错误保留已发生计数与失败，不自动重试。运行计划冻结候选数量和精确前向上限：`sum(3 + allowed_semantic_category_count)`，不得只估“约七次”。

原old80/old40已全部暴露，只能作开发/回归。比较必须同时报告漏检、误报、待审/阻断、完整遮蔽、物理前向和耗时；不能丢掉失败材料后报高P/R，也不据这些检测结果推断合法回答减少拒答、原生迁移成功或论文创新。

## 6. 标准方法依据

[Yin、Hay与Roth，EMNLP-IJCNLP 2019](https://aclanthology.org/D19-1404/)已用文本蕴含统一零样本分类，故“标签改写为hypothesis＋NLI”是已有方法。[模型作者资料](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli)支持多语言NLI和该三分类顺序，并不保证字段/实体角色任务的效果。

[HF官方zero-shot pipeline](https://huggingface.co/docs/transformers/main_classes/pipelines#transformers.ZeroShotClassificationPipeline)在`multi_label=True`时按E/C二分类归一化，在False时跨候选标签归一化；本机5.5.4源码与此一致。本合同直接使用原始三分类NLI，保留neutral和多断言共存；这是可审阅的保守工程判定合同，不包装为新理论。
