## 2. P2：显式“不完整”调用计数被改成“完整”，并进入缓存

**位置：**[privacy.py:423](../memory_migration_study/privacy.py#L423)至464；下游为[严格类别门禁](../memory_migration_study/memory_labels.py#L554)及[缓存准入](../memory_migration_study/detection_cache.py#L106)。

检测适配器返回下面这样的结果时，`detect_sensitive`只检查`local_calls`是不是范围内整数，没有读取适配器明确给出的`local_calls_complete=False`：

```json
{"status":"ok","findings":[],"errors":[],"local_calls":1,"local_calls_complete":false}
```

独立复现输出：

- 输入适配器：计数不完整；上层检测结果：`status=ok, local_calls_complete=True`。
- migration、generation和two_stage三种严格类别模式，均得到`status=ok, egress=ok`。
- 缓存将该响应存为成功检测，第二次调用直接命中，记录为0次新增调用。

**实际影响：**调用记录的完整性被提升，严格处理门禁和缓存准入接受了本应保留为不完整的状态。可能造成调用/成本低报，或者将不完整响应复用为正常结果。反例只用普通合成文本，不构成已经发生语义漏检或授权绕过的证据。

现有内置组合适配器往往还把计数设为`None`，因而避开这一路径；具体触发条件是“计数标量看似有效，同时显式声明不完整”。缺失该字段的旧适配器兼容性是另一个问题，不能不分情形全部改成失败。

**现有测试为何没抓到：**计数合同测试主要检查整数范围；`test_strict_labeled_transfer_contract.py`是在检测返回后再patch不完整状态，绕过了实际丢字段的位置。独立反例经第二审查路径再次确认。

**修复优先级：先修。**保留必要的旧字段缺省兼容，但对显式False或非法完整性字段保留不完整状态，不允许严格完成或缓存存储。增加从适配器原始返回值进入validator的端到端测试，覆盖多来源聚合、缓存命中以及不完整状态，而不是只patch最终结果；不要把计数不完整误称为语义不确定。

## 3. P2：总时限不是硬截止，源标注最后一请求超限仍可标完成

**主要位置：**[源标注执行器:418](../scripts/run_source_annotation_probe.py#L418)。该执行器在每条开始检查时间，最后一次请求返回后没有统一末检，就进入预测封存、评分及完成报告。

独立纯内存反例使用24条合成输入：最后一次POST从1799秒开始，在1805秒返回，注册总时限是1800秒。实际client、迁移准备、评分、封存和报告代码仍执行，最终记录：

```json
{"registered_seconds":1800,"actual_synthetic_seconds":1805,"report_status":"complete","rows":72,"posts":24}
```

另外，Qwen3.5全文、copy/tag和采样三个新client会在返回后拒绝越限，却只在建立连接时一次性设置socket超时。socket空闲超时不等于整条请求总截止：请求、响应头、正文各自未超过空闲时限，合计仍可超过剩余预算。独立假HTTP/时钟反例在1799秒开始、1801.25秒才被事后拒绝；如果正文持续小量到达，单纯空闲超时也不能保证总时限。

**实际影响：**源标注可以错误宣告符合时间预算的完成；其他三个client虽不伪造完成，但无法兑现硬停止上限。这是预算与执行状态合同问题，不是模型分类能力问题。

**对旧结果的核查：**四个保存批次耗时分别约22.110、26.531、12.891和32.719秒，均远低于1800秒，没有证据表明上述超时缺陷影响了它们。本次没有改旧分数，也没有新增真实HTTP或模型请求。

**修复方向：**传递同一个绝对deadline，使用可中断I/O或总截止看门狗，封存预测和写完成状态前统一末检；超时/中断与完成明确分开。若要求模型服务端也立即停止，应另验证取消机制，不能只凭客户端socket关闭作保证。新增“最后一条越限”和“连续进度但总耗时越限”的无网络测试。

本机复现脚本：`results/code_cross_review_20261028/experiments/experiment_integrity_repros.py`。成功制品：`experiment_integrity_repros_run02/summary.json`及其`source_last_request_overrun/`目录。初次审查脚本有一处payload构造错误；保留run01，仅修复反例输入后在run02成功，不修改生产代码。
