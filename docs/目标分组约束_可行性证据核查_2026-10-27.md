# 目标分组约束的可行性证据核查

日期：2026-10-27。范围：当前已测 Cognee 1.6.5 与 Open WebUI 0.12.3，自托管安装与固定官方源码。仅静态读取文件和公开资料，未启动后端、未导入厂商模块、未执行数据库操作、未调用模型。

**结论：目前未取得这两个已测后端存在全局分组数量 K 上限的证据。项目中的“两数据集”来自研究 worker 自限；不能用它证明原生产品需要 K 预算优化。** 新参考实验中的 K 应继续标为模拟参数，不能标为确认的产品限制或组织预算。查不到上限不证明资源无限，也不排除未审计配置、托管套餐或组织管理约束。

## 2. 权限粒度、计数单位与真正的限制

| 核查项 | Cognee 1.6.5 | Open WebUI 0.12.3 | 对新方案的意义 |
|---|---|---|---|
| 当前验证路径的授权对象 | dataset；可向user或role授予read/write/delete/share | Note等具体resource；grant支持user/group/公共主体与read/write | “一个分组”不是两边天然相同的资源单位 |
| 能否直接给用户授权 | 可以，dataset权限接口接受principal | 可以，同一Note可配置多个user grant | 不一定需要为每一读者集合另建原生role/group |
| 多人共享是否必然复制内容 | 否；给同一dataset新增ACL不复制其内容 | 否；同一resource_id多个grant仍是同一Note | ACL条目、角色、容器、内容副本需分别计数 |
| 跨容器放置内容 | Data行按dataset隔离；同内容跨两个dataset形成不同Data行/ID | 新建两个Note形成不同Note记录；同一Note加grant无需新Note | 逻辑记录数与物理字节量也需分别测，不能直接当同一费用 |
| 总数量上限 | 已查创建dataset和role路径未见总量配额检查 | 已查创建Note、保存grant及相关配置/组路由，未找到可支撑当前K的总量配置 | 不据此声称无限；只说明目前K缺乏产品证据 |
| 研究夹具限制 | 投影worker自行要求dataset数小于2 | 投影worker只接受readonly/managed两个逻辑dataset | 属实验控制，不是产品上限 |
| 分页限制 | 查询限额须按相应接口解释 | Note列表page模式limit=60；模型列表亦有分页limit | 分页大小不是最大容器数或最大授权组数 |
| 隐式/继承读者 | 直接、role、tenant授权会合并；创建Agent数据集时有效父用户也获全权限；父用户还可达其Agent显式授权 | Note读取含owner/admin路径；grant检查考虑直接用户、公共授权和继承group成员 | 有效读取集合不能只由规划器输出的显式读者生成 |

## 4. 对问题成立的裁决

在开放式自托管环境中，若允许创建主体专属容器/直接ACL，预算也没有被真实限定，普通精确授权映射可作为充分强基线。新算法不能通过人为删除这些可行方案来获取优势。

真实研究约束不一定必须是厂商硬上限，也可以是可证实的组织管理预算或原生部署成本；但需有独立依据，并把K换算到对应实体：
- dataset/Note数；
- role/group数；
- ACL grant行数及变更次数；
- Data/Note副本数；
- 实测存储量、查询/写入开销。

这些量不能互相替代。尤其Cognee的role是授权主体，dataset是受保护容器；WebUI的group是主体集合，Note是受保护资源。将“角色数量受限”与“记忆容器数量受限”视为同一问题，会改变可行空间。

**当前建议：保留小规模纯离线参考验证，但现实场景门槛未通过，不启动以真实K为前提的新算法效果主张。** 可以证明模型/检查器一致，不能据此证明产品必要性、模型任务提升或论文创新。
