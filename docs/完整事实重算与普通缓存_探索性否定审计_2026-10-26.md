# 完整事实重算与普通缓存：探索性否定审计

2026-10-26。目的：在继续设计新算法之前，先排除标准强基线已经解决的问题。本轮只读审阅既有核心，新增一个独立探索脚本；没有修改默认、冻结的源事实卡或恢复逻辑，没有读取 fresh64，没有调用模型、付费 API 或原生客户端。

## 结论

**目前没有找到能击败“完整事实级当前权限重算＋普通缓存”的功能性反例。** 给定同一份正确完整的事实和来源结构，标准重算与普通缓存均能处理本轮全部受控情形。独立来源、AND/OR 支持、同值异关系与撤权后合法保留，不宜单独继续作为新算法主张。

当前工程确有保守粒度限制，但它们是具体实现限制，不是上述强基线的缺陷。既有近邻备忘已经要求比较完整重算与正常缓存；本轮结果支持该要求，没有新增文献新颖性结论。

## 1. 当前代码实际做到了什么

- `MemoryLabelAuthority` 将授权绑定到确切原文、范围、主体、执行 Agent 与生命周期；`validate_access` 可再次调用服务端当前授权检查。已有生命周期见证已验证两条预先存在的合法授权，撤一条后新上下文可保留原来的另一条。
- `prepare_labeled_transfer` 在处理前核验全部传入记录。`restore_labeled_answer` 在恢复前同样核验完整记录集合，不能把恢复映射裁成有利子集。
- 假名化在一次请求中按实体值统一代号。同一值出现在不同来源时，其代号汇总全部来源依赖，恢复采用保守的全部获权条件；不会自行猜测来源独立性。
- 源事实卡保存角色、值及锚词的同记录原文位置，并保留完整上下文。它尚不抽取完整的“主体—关系—宾语—版本—否定”原子，更没有通用多来源 AND/OR 证明。原子支持结构需要独立构建和核验，不能因为有卡片就声称已经具备。
- `DetectionCache` 缓存的是成功校验后的敏感跨度，不是权限。当前核权、规则、出口检查与恢复仍执行。其当前作用域包含完整授权集合及生命周期，正确但可能发生较宽的缓存失效。

## 2. 新增的零模型资格实验

脚本：`scripts/probe_complete_fact_cached_baseline.py`。最新记录：`results/complete_fact_cached_baseline_20261026_v2/report.json`。

它使用本项目真实的签名记录和当前授权检查；事实语义、独立来源、复制血缘、完整支持集合与服务器版本通知均由合成夹具提前声明。**这是“给定正确结构”的机制上限，不是自动抽取来源的效果评测。** 这些输入对两个标准基线完全相同，没有用弱化的 `any-source` 或只比金额字符串的实现充当主对照。

| 受控条件 | 完整事实基线应有的行为 | 本轮结果 |
|---|---|---|
| 一个来源支持客户和预算，另一个只独立支持客户 | 撤前者后只保留有完整依据的原子 | 通过 |
| 另有预先存在的完整预算来源 | 撤第一来源后仍保留预算 | 通过 |
| 同一预算还可由两个共同必要来源支持 | 一个 AND 成员撤回后，该支持集合失效 | 通过 |
| 相同金额属于其他项目、预测版本或否定事实 | 不得替代原项目的批准版正事实 | 通过 |
| 同一组织同时是客户与承运方 | 承运关系不能补齐已失去依据的客户关系 | 通过 |
| 复制件有自己的记录 ID | 原根撤回后不能把复制件算作独立来源 | 通过 |
| 同一事实有两条独立当前授权路径 | 只撤一条时保留；两条都撤时停止交付 | 通过 |

7 个原子、7 次状态、每状态重复 2 次，共 98 格，两组均与预先写定的参照一致，选择的见证也相同。98 是相关工程检查格数，不是独立故事或任务成功样本数。普通缓存为 83 次命中、15 次未命中；每次实际交付仍重核所选来源，缓存不赋权。

纯结构评估阶段记录的当前检查数为完整重算 120、普通缓存 23。这个数字没有把交付重核、版本通知、失效维护、真实后端请求或端到端耗时合并，**不能作为新方法性能收益**。它反而说明：应当把正常依赖缓存纳入强基线，不能用“每次重复所有工作”的人为弱版本制造增益。

同时重跑现有本地独立授权生命周期见证，21 项工程检查全部通过，模型调用为 0。已有基线已经保留预先存在的独立合法来源，不需要在撤权后补签新授权来提高结果。

## 3. 两个真实的当前实现边界

**同值、不同关系共用一个代号。** 受控记录分别为客户和承运方，组织名称相同。实际投影产生不同角色卡、一个相同值代号。撤回承运记录后，旧客户卡被 `source_access_grant_revoked` 阻断，原恢复被 `grant_revoked` 阻断；仍合法的客户信息也暂时不能经旧上下文交付。标准做法重新筛选当前有权的原客户记录，创建新请求、原样走准备与恢复，立即成功。没有裁旧映射、补授权或让旧回答换来源追认。

这表明旧上下文采用保守全依赖语义，不能据此声称完整事实重算会丢掉所有合法信息。若未来要选择性恢复，必须先证明回答关系的完整来源，且与同等事实级基线比较；仅把所有值依赖从 AND 改成 OR 会破坏同值异关系和共同必要来源的边界。

**无关撤权也会使旧源卡失效。** 另一控制请求只含客户来源 S2；撤回完全不在请求中的预算来源 S4 后，S2 仍然获权，原完整恢复仍成功，但旧卡表因全局生命周期哈希改变而被 `source_card_context_changed` 阻断。按当前状态普通重建源卡和投影即成功，不需要模型。这是可定位的缓存/绑定粒度限制，可作为后续工程优化候选；不能包装成新的授权理论或来源图算法。

## 4. 若继续研究，最小实验与停止条件

下一步如保留该路线，先固定完整原子及支持候选输入，比较三组：完整当前重算、正常依赖缓存、拟议增量实现。三组共享真实授权参照、源检测、完整关系匹配、正常缓存机会和恢复合同。先用上述受控事件验证正确性，再决定是否值得研究实际语义结构抽取。

只允许把**实际测得的额外贡献**作为主张，例如在同等安全与合法效用下，降低真实远程核权/重建次数。需包含缓存命中与失效维护、版本获取、事件缺失后的完整重算、跨主体隔离、撤权发生在回答途中时的阻断，以及新请求保留合法信息的全部成本。可信通知与未改变状态的承诺要对三组对称。

以下任一情形成立便停止新算法路线，保留工程适配或负结果：

1. 完整重算＋普通缓存同样安全、合法效用相同，实际总成本相同或更低。
2. 优势仅相对宽松 `any-source`、按值查找、无缓存、只级联全删或事后补签的对照。
3. 必须读取评分答案才得到完整原子或支持结构；或只有手工结构上限，实际抽取不能满足要求。
4. 必须裁剪完整原映射、放宽原恢复规则、把复制当独立、以其他项目/版本的同值补关系，才能保留成绩。
5. 假定可信版本和事件送达却不计其成本；事件漏报后仍复用旧授权；或把旧上下文拒绝等同于新上下文永远不可用。

当前应优先保留这份否定证据，而不是给标准 AND/OR 来源表达、反向依赖索引或缓存换名。上述资格实验不替代原敏感检测、云端配对、原生稳定性、独立保留集与论文创新验收。
