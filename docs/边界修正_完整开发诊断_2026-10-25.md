# 边界修正：完整开发诊断

日期：2026-10-25。目的：把已经实现的字段结构、金额组合算法接入实际检测、假名化和外发校验，检查改进是否仍能留在最终结果中。本文件先记录执行方案，结果在执行后追加。整体效果验收目标保持不变。

## 1. 本轮改动与适用范围

新增可选 `boundary_detector.detect_with_boundaries` 入口，原有默认路径不变。处理顺序：

原检测（规则＋本地编码器）→ 按具体位置纠正边界 → 原检测层的边界扩展与重复值传播 → 原假名化准备 → 原外发检查 → 原恢复接口。

重整使用三类证据：

- 具有相同类型的候选位于明确字段值内时，补全到该字段值；没有候选的字段不自动标为隐私。
- 候选恰好位于解析出的字段键内时，按该位置辨认字段名。不会把“客户”“reference”等词加入全局排除表；真正叫这个名字的对象仍受保护。
- 金额的两个部分只有在同一来源、同一个数字位置和同一种币种时才允许补全。

跨到下一字段的过长候选，只在剩余部分全部由真实字段语法或独立的敏感候选覆盖时修正；无法解释的部分使整个处理进入待审。不会单凭换行截断。

显式业务敏感词表的约束继续生效，结构解释不能把它降级。输入绑定错误、原检测失败或计数缺失均不能被回放升级为成功。主体授权、问题独有内容不得成为记忆证据、撤权检查和伪造代号阻断继续由旧接口执行。

## 2. 执行前固定的比较

使用已经暴露的原开发集全部80条：中英文各40条、58个敏感完整跨度。此集合只用于开发，不能改名为独立验收集。

| 条件 | 作用 |
|---|---|
| host_baseline | 原 GLiNER＋规则最终检测结果 |
| rehost_noop | 同样结果再经原主机规范化，检查回放本身是否改变预测 |
| boundary_refined | 相同输入经边界修正，再经原主机规范化 |

每条材料的三个条件都实际经过 `prepare_private_payload` 和 `validate_outbound`。真实替换后的文本通过已有 `masking_intervals` 工具逐段核对，问题和记忆均计入，不只扫描完整秘密字符串。恢复映射仅在进程内使用，不写入结果文件。

先使用保存的主机最终检测结果进行零模型回放。保存文件已包含规则合并、传播和包含关系处理，**不能称为原始 NER 输出**。如果工程检查和回放核对无误，再运行固定版本本地编码器，对相同材料进行真实重新检测；每个非空受限来源分别计一次编码器调用，三个条件共享该结果，不重复计费或虚增样本。

## 3. 评分与边界

- 完整 source/start/end/category 精确匹配，保留 TP、FP、FN、语言、类别和公开/私有策略分组。
- 所有失败材料的参考敏感跨度仍留在召回分母。
- 同时统计实际完整遮蔽、部分遮蔽、未遮蔽/未就绪、误遮蔽字符以及仪器错误。
- 原开发目标仍是召回率≥95%、精确率≥90%、无待审/处理错误；达到开发目标也不代表新独立验收通过。
- 全部检测和准备完毕后才解析评分标签；不得把标签、参考答案或评测敏感词表传入检测器。
- 本轮不调用云端模型；没有新回答生成，就不能声称合法问题拒答减少。

此分支保留旧重复字串传播机制，因此真实名称与字段键同词时，键仍可能再次被遮蔽。该现象必须记录，不能通过取消外发检查来得到“更好效果”。输入与输出哈希用于绑定和可复核性，不是身份认证或数字签名。

## 4. 完整目标仍需完成

本轮是开发阶段的机制修正。原40条保留集和16个故事已被查看，也只能作为回归。方法最终冻结后仍需新的独立材料；下游任务需要真实生成，完整云端对照需要满足原调用数及预算约束，并与本地结果分别报告。不得用本轮代码测试、回放结果或局部遮蔽通过替代整体效果验收。

全工程离线回归命令 `python -B -X utf8 -m unittest discover -s tests -q` 完成：689项通过。该结果证明本轮覆盖到的工程行为未回归，不证明检测泛化、合法回答正确或论文创新。

独立核验收据位于 `results/acceptance_v2_research/boundary_fresh_v1/independent_verification.json`：37/37项通过，覆盖两次运行全部480行、原输入、50份包源码和2份脚本的归档哈希、实际替换轨迹、分组评分与调用计数。敏感字符实际覆盖897→897，新增覆盖和新增放开均为0。[公开聚合记录](../benchmarks/boundary_refinement_20261025_summary.json)不包含原文、模型回答或恢复映射。

结论：本轮验证了实际管线上的边界改善，但开发精确率尚未达到90%，原局部泄露仍存在，未运行本轮回答模型；**整体效果验收未成立**。后续应针对真实完整实体提取和语义角色误判继续开发，再做新材料及下游回答验收。不能通过排除“空壳、客户”等字符串或改评测答案来消除误报。

## 6. 另行修正：字段名不能单独作为业务事实的恢复证据

联审中发现并用真实旧接口复现：问题提供 `Customer`，记忆只有 `Customer:` 字段键。旧传播机制把问题中的值遮到记忆键上，随后可能把键当成事实来源，允许恢复 `Customer`。这是事实来源判断错误；本例没有跨越主体访问权限。

新增可选 `boundary_preparation.prepare_boundary_payload`。它先完成原准备流程，再检查每个代号在记忆中的实际替换位置。如果某来源的全部同值替换位置都在明确解析出的字段键内，仅移除这个来源的“事实支持”关系。字段键仍被遮蔽，权限和外发检查不变，也不会新增任何来源。

实际对照位于 `results/acceptance_v2_research/boundary_preparation_v1/`：

| 自编机制见证 | 旧准备 | 新准备 |
|---|---|---|
| 问题提供值，记忆只有同名字字段键 | 错误允许恢复 | 拒绝：没有记忆值证据 |
| 记忆字段内确有同名真实值 | 允许 | 允许 |
| 同时存在字段键来源和独立真实值来源 | 允许 | 允许 |
| 撤回仅含字段键的来源，真实来源仍有效 | 拒绝 | 允许 |
| 真实值来源也撤回 | 拒绝 | 拒绝 |

三组故事的旧新对照共6行，撤权为进程内 authorizer 状态变化，不是原生系统在线撤权实验。这个约束针对单个业务事实值问答；询问字段结构/表头本身的任务需要单独的证据类型，不能称为一般语义证据安全方案。

另外，原80条开发材料的每个新旧准备条件都实际运行，共160行。两条件均80/80可准备，完整遮蔽仍57/58、部分遮蔽1/58、误遮36字符，没有评分变化。该批材料中新增来源剔除次数为0；机制收益来自上述自编见证，不能推广成整批合法回答改善。新增编码、生成及云端调用均为0。

可选接入顺序为 `detect_with_boundaries → prepare_boundary_payload → validate_outbound → 原恢复接口`。当前默认实验保持原方法，避免把尚未达到整体目标的候选包装成已验收版本。

来源修正完成后，同一全工程离线回归命令再次完成：**710项通过**（51.729秒）。旧的689计数对应来源修正之前的时点，两次测试不相加。

准备阶段独立收据 `results/acceptance_v2_research/boundary_preparation_v1/independent_verification.json` 完成21/21项核验：全部160行实际替换轨迹、80对评分、6行机制见证、输入/源码归档以及无恢复映射持久化。该收据不把机制见证当作真实模型问答成绩。
