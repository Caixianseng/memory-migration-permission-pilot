# 双客户端语义记忆迁移复核

2026-10-27。基线提交：`8af5e9eb32c5eb80d0f904f59c9d942110951a89`。实现和执行由 GPT-6.1 Sol 完成；被测客户端为本机 Qoder 1.1.77 与 DeepSeek Harness 0.2.1-rc.3。

## 1. 结论与两种成绩口径

**本轮没有复现先前 Qwen 在假名化预算负责人问题上的幻觉。** 两客户端各 12 次、累计 24 次真实客户端尝试：合法事实选择 **16/16**，缺失信息返回 UNKNOWN **8/8**。八个“客户端 × 源/目标 × 原文/假名化”格子都为合法 **2/2**、缺失 **1/1**。全部结论来自同一个已暴露英文开发故事，只有三道不同的逻辑问题，不能将 24 次回答当成 24 个独立故事。

这个语义合并结果含 **首轮 2 份旧原生回执的零模型事后重评 + 承接轮 22 次新调用**。原始调用当时的完整工程流水线是 **23/24**：第 2 个位置被新增驱动误判为“记忆加载证据不足”，首轮保持 `engineering_failed`，没有改写成成功。Harness 自身已成功回答，事后核实原生 SHA-1 加载摘要与文件 SHA-256 后，该回答在承接轮的新受控主机能力下重新核权、恢复并评分。**这不等于原调用当时已经恢复成功，也不属于原生在线撤权证据。**

没有观察到同一客户端源/目标答案差异，也没有观察到双向跨客户端配对差异。两种比较都只支持本轮受控互通与效用；相同主机构造输入不能消除客户端隐藏上下文、提供方部署、会话运行和原生系统提示差异。两个客户端都选择 DeepSeek Flash，不能称为两个独立模型的复现。

## 2. 已冻结材料与真实迁移链

依据 [双客户端语义复核预注册](双客户端语义复核_预注册方案_2026-10-27.md)，仅使用公开自编合成故事 `dev_en_paraphrase`。四条竞争事实依次为 Juniper Field 的最终审批人、备用审批人，以及 Maple Haven 的主要联系人和替补联系人；每次均提供全部 F1–F4，问题顺序不变，输出合同为 `{"answer_id":"F1"}` 至 F4 或 UNKNOWN。

四卡仅放在原生 `AGENTS.md` 中，原生提示保留原 reader 的完整 SYSTEM、Flat-ID 规则和问题，并指向本地事实卡。没有把事实重复塞入问题提示，也没有提供评分参照、期望 ID 或题族。原文只有虚构公开材料，没有读取用户私人内容。

每个“方向 × 问题 × 表示”有独立源/目标 Git 根，共 12 对工作区。主机先写实际源 AGENTS，再从源文件重读四条精确事实跨度，建立 `NativeAgentBroker` 记录并导出统一包；包落盘后重读并验证 HMAC、主体、工作区、当前记录和约束，再从实际包导入目标 AGENTS，最后重读目标核对四候选和源/目标字节相同。目标事实没有从故事夹具补出。源事实由可信主机预置，不称源 Agent 自主生成。

两端分别依据实际读得的源/目标正文建立独立 CurrentMemoryAuthority、签名记录、请求能力和恢复映射，然后生成最终原文或假名化 AGENTS。每个主体、题目、方向和阶段的私有恢复映射都独立且只在内存；同逻辑题只共享模型可见代号投影。最终源/目标 AGENTS、完整主机提示和全部顺序在任何本轮调用前冻结。每题在两方向使用相同可见 nonce，使同一客户端跨阶段的主机构造输入也可精确比较。

假名化仍使用既有长 `[PVT_…_CUSTOMER_…]` 形式，人名和项目均标 CUSTOMER。它同时改变名称、长度和粗类型信息；本轮没有分离这些因素，也不是旧 Qwen 失败 wire 的精确重放。新 nonce 已预先固定。标签来自完整合成登记，不报告新的敏感检测 P/R。

`NativeAgentBroker` 和 CurrentMemoryAuthority 在此是**受控本地主机参照**。静态 AGENTS 只测客户端内容互通和回答效用，不能证明厂商原生逐次 ACL、即时撤权、企业 Agent IAM、自动长期记忆或真实跨机网络。

## 3. 首轮工程错误与承接处理

首轮 plan/run_01 冻结上限为 24。位置 0 的 Qoder 原文 Q1 完成；位置 1 的 Harness 原文 Q1 也返回 `{"answer_id":"F1"}`，但新驱动额外比较原生加载摘要时，将 40 位 **SHA-1** 摘要当成了文件的 64 位 **SHA-256**，遂立即停止。已用 2 次，剩余 22 个位置保留为未运行。没有自动重试，没有归咎 Harness 产品。

只读诊断确认：原生基线的 SHA-1 `d6621b250e3bbd29da2dc038e0c9ae2c62b6fc63` 与实际 AGENTS 匹配；基线正文、文件和 wrapper receipt 的 SHA-256 都是 `5065f391049e73274326f87a10ab639942c995eb6fa5e21e3c41c1438513460e`。Harness wrapper 状态成功、native instruction loaded 为 true、单 SDK 流为 1，原凭据未变且临时凭据删除。

随后冻结独立承接 plan/run_02，绑定父计划、已关闭预测、诊断、两个真实结果/预算回执和两份 AGENTS 的哈希，复用父计划全部 24 份输入、nonce 和顺序。预算继承已用的各客户端 1 次，只启动原位置 2–23 的 **22 次**，累计仍为 24、每客户端 12。旧位置没有重新请求模型。

首轮两份回答接受零模型事后回执重评；再次恢复使用承接轮的新受控主机能力，并保留 `original_status`、`original_failure_class` 和 `original_restoration_status`。首轮原始计划、源码快照、预测、摘要和错误没有改写。承接的 22 个新位置全部在当次正常完成。承接摘要状态明确为 `completed_with_disclosed_parent_engineering_failure`。

运行前另完成正式执行入口与测试替身的隔离、回执身份/限制器验证、冻结参照读取和源码漂移失败关闭；这些是实验驱动工程修正，不是已发现的产品安全漏洞。承接关闭后，根代理将普通入口修为官方 SHA-1 baseline 与本地 SHA-256 文件/回执的独立绑定，并同步测试的成功/混淆反例。首次发布修正只改普通驱动和承接测试两个文件；相关测试 **37/37** 通过。两轮 `frozen_source` 原件保留，发布修正没有增加客户端调用。

## 8. Windows CI兼容修正

首次GitHub发布提交`9e370d2`的Ubuntu自动测试通过；Windows出现31个错误，均发生于新测试夹具初始化时的`result_scope_or_link_invalid`。在本机真实Windows junction临时目录中，两个代表测试复现了同一错误。修复仅将两套测试的临时根改为`Path(self.temp.name).resolve()`，生产路径守卫保持原样；同一别名目录下全部37项相关测试随后通过，0失败/错误/跳过。证据见`results/native_ci_fix_targeted_summary.json`。CI具体临时目录是短名还是junction，日志没有区分；本机复现证明的是非规范别名路径触发同一合同。

另将公开请求限制器的JavaScript文件固定为LF，避免Windows的`core.autocrlf=true`检出改变被清单绑定的字节。修正前检出过滤结果与manifest不符；修正后true/false两设置均匹配。两项修正没有启动任何客户端，不改变24次回答及原始失败记录。前述1731项本机全量回归对应CI修正之前的发布快照；修正后提交的完整自动回归结果以GitHub Actions对应提交为准，逐次结果保留于本机。
