## 2. 尚未测试的是哪一个机制

当前 [relation_occurrence.py](../memory_migration_study/relation_occurrence.py) 的 `GlinerOccurrenceRuntime.propose` 先调用组织实体提议；`classify_document` 再通过 `schema.classification` 与 `model.extract` 对目标位置作文档分类。名字虽然含有 relation，但它不是原生 `JointIE`。

已测的原生片段属性方法使用 `entity_attributes`，先取得实体，再为该位置评分属性；它同样不是原生 `JointIE`。这些方法的候选缺失、边界错误、关系误判和大量待审已有真实负结果。本次没有重跑或修改这些结果。

官方 `JointIE` 的机制不同：同一次编码产生实体与关系候选，再搜索满足类型等约束的图。固定源码中存在两个相关步骤：

1. `joint_ie/scoring.py::_score_boundary_relations` 从关系角色候选形成头尾实体对，并对这些端点调用 `score_explicit_spans`，产生 `extra_mentions`。
2. `joint_ie/engine.py::_decode` 对 boundary 候选调用 `candidate_score_set_to_problem(..., rescue_relation_endpoints=True)`。关系端点可进入后续图搜索，即使它未通过普通实体提议的候选门限。

因此，“独立 NER 没提到，但关系角色已有相应位置”的情况有一个未测的已有救援路径；**候选池之外的实体仍无法由解码器凭空补出。** 是否找回机构含义的“苔藓”、是否正确区分同名普通词和供应商，必须实测。

源码依据：[原始评分与 extra_mentions](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/joint_ie/scoring.py)、[候选端点救援](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/joint_ie/candidate_scores.py)、[引擎与解码配置](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/joint_ie/engine.py)。

## 3. 已发现的真实接口缺口：关系 description 未进入模型输入

固定 `JointSchema.relation(..., description=...)` 确实接受并保存描述。但固定 `joint_ie/compiler.py::compile_schema` 的 `model_schema` 只写入关系名和空的 `head/tail` 字段，没有构造 `relation_descriptions`，尽管它保留了 `entity_descriptions`。

另一方面，固定 `processor.py::_process_relations` 明确读取 `schema.get("relation_descriptions", {})`，并将对应描述作为 `prompt` 送入 `_transform_schema`。

所以，**仅在 `.relation(..., description=严格客户定义)` 中填写文字，不能证明模型收到该定义。** 图结构合法，也不能弥补实际输入遗漏。这个静态缺口不自动解释此前分类/属性实验失败，因为它们走的是其他接口。

可考虑的最小适配是不改 vendor，只补齐交给原生评分器的编译结果：

```python
# 拟采用的适配示意，未执行；不是新的解码或识别算法。
compiled_original = joint.compile_schema(schema)
model_schema = deepcopy(compiled_original.build())
model_schema["relation_descriptions"] = deepcopy(trusted_relation_descriptions)
compiled = replace(compiled_original, model_schema=model_schema)
```

这里的 `replace` 为 `dataclasses.replace`。真实 `CompiledJointSchema` 是 dataclass；引擎 `_is_compiled` 接受该编译对象，避免再次从未补齐的声明 schema 编译。不得原地修改共享缓存字典。

描述只能来自预先固定的可信 policy、类别定义和业务 scope；不能含评测答案、人工补入的候选名、某条材料的关系标签或按 ID 选择的提示。字段补齐的作用只是让同一既定语义合同实际进入编码，不是引入新事实。

进入推理前必须核验最终 `compiled.build()`、实际 `schema_tokens_list` 与完整 `input_ids`：既要证明关系描述已进入编码，也要证明原始业务 scope 和当前/历史/否定定义没有在编译过程中丢失。只保存声明 schema 的 JSON 或哈希不够。

源码依据：[声明 schema](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/joint_ie/schema.py)、[编译器](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/joint_ie/compiler.py)、[processor 的描述输入入口](https://github.com/fastino-ai/GLiNER2/blob/ca4f68235b50fe4c3ecf3876851d748fe4b15c6c/gliner2/processor.py)。

## 4. 最小冻结设计：先做已有强基线的资格检查

以下是待审设计，不是已经冻结或启动的实验。优先使用 8 个已暴露诊断 ID：`[1, 4, 6, 11, 13, 16, 19, 22]`。它们包含 6 个参考可确定案例和 2 个关系未知案例；只用于机制诊断。完整材料池为既有 24 条正文，20 个可确定、4 个未知。不得将这些已看过的材料称为独立验收集。

### 4.1 输入及业务实体

使用同一严格客户关系 policy 和完整原始正文。不能从 gold、登记敏感值、旧模型答案或问题文本提前给出实体。固定定义两种实体类型：

| 类型 | 来源与含义 |
|---|---|
| `external_organization` | 正文中的具体外部机构名称，保留完整名称与法定后缀；同词的植物、普通动词或泛称用法不属于该类型 |
| `scope_company_mention` | 正文中指向可信业务 scope 的实际出现位置，例如 `we/us/our company/本公司`；不是宿主额外插入的实体或伪造 offset |

我方指称作为关系端点不意味着它是应遮蔽的外部客户名。模型给出的机构性、关系和置信度均不能赋予读取、共享或转授权权限。

### 4.2 有向关系与三值判定

关系的头为 `external_organization`，尾为 `scope_company_mention`，固定区分：

| 关系概念 | 允许的确定性解释 |
|---|---|
| 肯定的当前客户 | 外部机构现在向我方购买，保护相应机构名称的精确出现位置 |
| 肯定的历史客户 | 正文明示曾向我方购买；即使当前合同终止，仍按既定 policy 保护 |
| 明确从未是客户/客户记录错误 | 必须有明确否定证据，且没有肯定的过去或现在客户关系，才可据此作非客户判定 |
| 外部机构向我方供货 | 只证明供应方向；单独存在不能推出其从来不是客户，因为同一机构可以同时是供应商与客户 |

不能把“现在不再是客户”改写为“从未是客户”，也不能把反向供货、没有预测到关系或低置信度当成明确非客户。

以下情况必须保留待审/处理阻断：空候选、空关系图、缺少我方 scope 端点、`feasible=False`、同一实际对象的肯定与“从未”证据冲突，以及仍存在未能裁决的外部机构候选。**空图不等于无敏感信息。** 这个保守方案也可能阻断本来合法的普通材料，必须完整计入可用性分母。

保护标签只投影到模型输出并由原文核验的精确跨度；不能因为字符串相同而同步标记其他普通词出现位置。当前步骤没有解决一般实体共指、跨窗口关系、时间逻辑或独立授权路径。

只使用类型端点和无自环等合理结构约束；不强加“一个公司只有一个客户”、互斥供应/客户角色或不符合业务的唯一性规则。结构约束的正确性和模型关系判断的正确性分别评价。

### 4.3 固定资源、真实 API 与上界

| 项目 | 建议一次冻结值或边界 |
|---|---|
| 加载 | 沿用 `LocalNerRuntime(.runtime/github_ner, threads=2)`；它离线加载固定资产。再用真实构造接口 `JointIE(ner.model)` 包装同一模型，避免第二次加载 |
| 设备 | 首轮 CPU、标准 attention、串行、既有 CJK-aware splitter；不同时运行 4B 生成模型，不切换分词或量化方式 |
| 解码 | `optimizer="beam"`、`beam_size=32`、`candidate_threshold=0.05`、`relation_role_threshold=0.05`、`top_k_entities=32`、`top_k_roles=12`、`relation_pair_cap=128`、`batch_size=1`、`max_len=None` |
| 实体/关系决策门限 | 一次固定为 0.5；不按结果扫参。checkpoint 内部候选池/关系对限制保持原配置，不等于外部配置可无限扩大 |
| API | `joint.compile_schema(schema)`；补齐并核验编译对象；`joint.extract(text, compiled, config=config, return_lattice=True)` 返回结果与本次同源候选证据 |
| 完整输入预检 | `model.processor.transform_record(full_text, compiled.build(), max_len=None)`；实际完整 `input_ids` 不超过 512，且所有选定材料先完成预检，随后才允许任何正式编码器推理 |
| 调用上界 | 8 条最多 8 次 extract、8 次编码器推理，无修复/重试；内部关系评分、显式端点评分属于嵌套工作，分别观测而不累加成独立样本 |
| 其他操作 | 新生成模型调用、云端、付费 API、模型下载、依赖安装、原生产品读写均为 0；可预声明 600 秒执行墙钟上限，超限保留未观察数量 |

`JointIEConfig` 的上述键、`JointIE` 对已有模型的构造方式和 `return_lattice=True` 均已在本机固定源码中只读核实；本轮没有执行这些调用。8 GB 显存不是本轮 CPU 方案的依赖。官方模型体积和此前 CPU 提取成功只支持资源可尝试，不等于联合接口已获运行资格或已有速度测量。

**不要虚构预检字段。** `TransformedRecord` 没有 `truncated_char_end`。固定 processor 明确规定 `max_len=None` 不截断；应记录真实 `input_ids`、`text_tokens`、`start_token_idx`、`end_token_idx` 和 `schema_tokens_list`。超长时阻断，不删除 policy、截断正文或临时改门限。

### 4.4 原文坐标与归一化

固定 `processor.transform_record` 会调用 `_normalize_text`，可能添加末尾标点；它不是新的源正文。需要同时保留调用方原文哈希、处理后文本和映射。

`RawScorer` 已处理调用方文本之外的合成后缀，但适配器仍须独立核对每个实体满足：`0 <= start < end <= len(source)`，且 `source[start:end] == entity.text`。输出采用原始 Unicode 码点半开区间。不得通过 `.strip()`、NFC、大小写转换、首次字符串搜索或错误位置修复掩盖坐标问题。

原生结果的 `head/tail` 指向图内实体 ID；应通过 `result.entity(id)` 取回真实端点，再验类型和位置。不能用同名字符串连接两个不同出现位置。

## 5. 对照、闭合和继续条件

首轮只作为原生强基线资格诊断，最多新增上述 8 次本地编码。可复用已经封存的 `qwen3_conditional` 同 8 条观察，但两者方法不同，不能称同模型纯解码消融；也不能重复计入新调用。

所有输出、实际输入、图候选、映射核验、真实脱敏准备结果和权限反例先闭合，再整体核验既有 24 条参考答案及两个 ontology，最后选择预声明的 8 个 ID 评分。所有失败、空图、待审与超限保留在原分母。

至少分开报告：

- 原文跨度的候选覆盖、精确 TP/FP/FN、同名普通词误标、供应方向与明确否定的错例。
- 关系端点救援的实际数量与位置；救援过的位置是否确实进入最终图和保护结果。存在 `rescued` 字段不自动证明找回了真实敏感实体。
- 已知案例可准备数、完整正确数、未知正确待审数，以及实际拟载荷中的漏遮/多遮和普通事实保留。
- 跨用户与跨 Agent 权限反例、真实编码和嵌套评分调用量、时延及失败阶段。

底层实际拟载荷的泄露与模型最后是否复述分别计分。本轮没有下游 Agent 问答，故不能报告拒答率降低、任务成功率提高或在线撤权成功。

如后续确需定位“关系端点救援”本身的作用，应另行冻结同一实际评分 lattice 的有/无救援解码对照，再衡量它的收益；不得把增加定义、降低阈值、改变候选 cap 和 beam 搜索的混合变化归因给单个机制。

推进到完整 24 条或新的独立材料之前，应先证明描述输入完整、原文投影准确、真实调用守界，并满足预声明的敏感保护与合法可用性门槛。失败则保留负结果，不调整参考答案或将全部阻断计作安全成功。
