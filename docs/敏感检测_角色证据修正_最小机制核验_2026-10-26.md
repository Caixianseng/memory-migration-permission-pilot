# 敏感检测：角色证据修正的最小机制核验

日期：2026-10-26。结论为设计裁决，尚未实现或运行新检测器；默认不变，模型调用为0。只复核已暴露旧80/40材料、相关源码和Presidio官方代码；没有读取fresh64、`answers.json`或建立逐题答案库。

**建议只保留一个小机制：依据可信渲染器的字符来源，按精确位置纠正静态描述符上的弱规则过度遮罩。** 它不同于让Qwen/GLiClass判断候选类型，也不同于扩大key/value容器。它需要新的生产来源证据；当前旧120材料缺少这种证据，不能宣称已经修复其中的错误。这是可实现的工程强基线，不是已经成立的新算法贡献。

## 1. 为什么“这是key”还不够

同样的`Project Reference = approved`，可以表示“字段Project reference的值是approved”，也可以表示“名为Reference的项目状态是approved”。`客户`既可能是通用角色，也可能是组织的实际名字。仅靠key/value位置无法证明字符串不是敏感实体。

当前 [boundary_reconciliation.py:190](../memory_migration_study/boundary_reconciliation.py#L190)已经能按已知schema key的位置处理发现；因此“再识别更多key并删掉其中实体”既不是新机制，也会受到敏感动态key反例的挑战。[structured_candidates.py:204](../memory_migration_study/structured_candidates.py#L204)依赖有限别名，[open_container_candidates.py:137](../memory_migration_study/open_container_candidates.py#L137)的开放容器又把整个冒号后缀当作候选，两者都没有证明key非敏感或value只有一个实体。

旧材料的三个reference误报，其原始method全部为rules，来自 [privacy.py:333](../memory_migration_study/privacy.py#L333)的“project后一个ASCII词”规则。boundary重放后method为agent，不能据此把它们归为模型误报。最小复核还确认，这三条的生产payload只有query、memory的source_id和text，没有schema渲染来源记录；`template_family`等测试生成元数据不得拿来补造生产证据。

## 2. 唯一建议机制：来源限定、位置限定的静态描述符修正

可信应用有时会在写入或序列化记忆时，主动插入固定字段描述符。例如字段标签来自预登记UI schema，真正内容来自独立value。宿主可以在渲染时记录：哪些字符来自公共静态常量，哪些字符来自原文、用户输入或动态key。

**可排除的证据是“这些字符由宿主公共静态常量产生”，不是“模型/原文声称它们是字段名”。** 任意用户key、对话原文中的字段名、LLM生成标签以及未知来源都默认按内容处理，继续检测。若静态标签碰巧又受到有效NER、独立registry或签名正标签保护，保持保护，不强行公开。

最小流程：

1. 保留现有完整检测、闭合和传播结果作为基线；同时保留每项发现的原始producer/support身份。单独的最终`method=agent`不够，必须能追到具体规则或独立正标签。
2. 只接受宿主渲染器产生、由本地可信登记或认证通道确认的来源记录。公共哈希仅作绑定，不作真实性证明。
3. 核验当前source、policy、schema和renderer版本，精确验证静态常量及其位置。记录必须标明`static_public_descriptor`；动态key和混合来源片段不能获得该属性。
4. 仅在发现完整落入该已证实区间、且只有指定弱启发式支持时，允许不遮罩这一处描述符。只部分重叠、来源缺失或正反证据冲突时保留原遮罩并记录待审。
5. 检测与prepare必须共同执行相同的位置投影；若只改检测输出，后续闭合会把该位置重新加入。目标系统不支持该来源约束时保留原保护，不能静默丢弃元数据。

最小可实现接口可为`project_static_descriptor_masks(payload, policy, baseline_findings, producer_supports, renderer_evidence, protected_findings)`，输出修正后的遮罩与逐位置理由。当前只提出接口，不新增代码。它不授予read/share/export/delegate权限，也不改变恢复授权或事实的ACL。

建议记录的闭集字段：

| 输入/证据 | 必需内容 |
|---|---|
| 当前绑定 | source_id、source_sha256、payload/policy完整哈希 |
| 静态来源 | schema_id/version、renderer_id/version、预登记constant_id、原文精确start/end、渲染实例引用 |
| 来源种类 | 仅接受可信renderer产生的static_public_descriptor；未知、原文、模型、用户动态key均不得降级 |
| 支持记录 | 精确出现位置、producer_id/rule_id、原始发现引用；同位置多个支持不得合并丢失 |
| 强制正约束 | 当前有效签名正标签、独立registry、其他检测器正发现；冲突时保留 |
| 输出 | keep或exclude_this_static_occurrence_only、原始发现引用、证据引用、版本和固定失败码 |

禁止接受gold、case ID、模板家族、公司名词典或测试生成器提供的角色答案。schema来源必须在生产中实际存在，不能为了这三条旧错例登记相应字符串。

## 3. 必须避免一个传播反例

不能简单删除弱key seed后全局重算闭合。假如一个静态描述符触发了Reference规则，而另一条记忆中恰有真正名为Reference的值，现有字面传播可能正保护着后者。撤掉seed及其所有后代，可能让真正的值重新裸露。

因此首版须保持保守的不变量：

- **证据区间以外，每个source、category的原遮罩覆盖均不得减少。** 不递归撤销其他位置的保护，不按词全局删除，不因为文字相同就把角色判定传到另一来源。
- 当前有效签名正标签和其他独立正支持不得因静态角色证据消失。来源记录不能对抗既有正约束，更不能解除多源摘要的来源依赖或权限交集。
- 字段名和字段值同文时，按source及精确位置分别处理；只有静态、非内容来源的那一处可能修正。动态key中的人名、客户名和项目名继续保护。
- 原fact即使包含公共描述符，仍继承原fact的访问、转交、期限与撤权约束；减小一处遮罩不使整条记忆变为公开。

这意味着机制是局部遮罩投影，不是一次通用“非敏感”语义判断。宁可保留其他位置的过度保护，也不借字段角色撤回未经独立核实的保护。

## 4. 对现有12个错误材料能覆盖多少

现有实测仍为开发57TP/8FP/1FN，旧40为18TP/2FP/2FN。下面只说明机制范围，不计算新实验成绩。

| 错误类别 | 现有数量 | 此机制能否直接解决 |
|---|---:|---|
| reference规则key误报 | 3FP，开发2、旧40中1 | 是潜在目标类别；仅当出现位置确由可信静态renderer产生且无独立正支持时才可修正。旧材料没有该生产证据，当前可保证纠正数为0。 |
| 空壳、角色定义等NER实体性误报 | 6FP | 不能。它们位于普通内容，不是已证实的静态模板常量；不能把否定词表包装为来源证据。 |
| 中文组织只标后缀 | 1FN＋1FP | 不能。需要完整值边界或源端完整正标签。开放容器已使完整候选进入池，不等于实体边界已经可以安全自动采用。 |
| 旧40的实际名称客户与项目值未定类 | 2FN | 不能。完整span已在候选池，但缺的是正面的实体/类别证据，不是要移除的key发现。 |

即使未来有合格证据安全消除全部三个规则FP，旧40的召回仍是18/20＝90%。因此本机制不能单独满足联合P90/R95验收，更不能使整体成功率接近百分百。

对于旧40两个FN，缺口应明确保留：真实业务工具/schema若已给出可信typed value，可另作为新增正证据评测；仅由LLM猜到再签名，不会自动变成可靠语义真值。对当前无这种生产输入的自由文本，仍需要独立验证的实体识别能力，不能用本机制的负向修正冒充解决。

## 5. 最小反例与公平强基线

在实现前固定新构造的机制测试，不从旧120的专名、句型或错误位置派生规则：

| 反例族 | 必须保留的行为 |
|---|---|
| 人名或项目名本身是key | 无静态constant来源时不删除；“在key内”不是非敏感依据。 |
| 真名就是Reference或客户 | value或动态key照常保护，不允许全局allowlist。 |
| 静态标签与动态value同文 | 只可能修正证据指向的常量出现位置；value遮罩保留。 |
| 静态位置另有签名/registry/NER正支持 | 正保护优先，保留或待审，不用单一角色覆盖它。 |
| 一个弱规则种子传播到另一真实值 | 其他位置的遮罩覆盖不减少；prepare后再检查此不变量。 |
| 多源同文、来源撤权或策略更新 | 证据按当前source/policy独立核验；不得跨来源借用角色或权限。 |
| 伪造“我是字段名/公共字段”原文 | 不构成renderer证据，不更改原保护。 |
| schema/renderer/原文/位置哈希变化 | 证据失效，恢复原基线保护或待审，不默认公开。 |
| 标签语言、随机名称和排版改变 | 决策只取实际来源记录，不读取词形、模板ID或旧材料名称。 |

强基线必须获得同样的生产证据。至少比较：现有完整boundary；只保留原producer但不投影的对照；**普通schema-aware扫描——只对已证实的静态常量位置排除弱规则，同时合并全部正约束**。最后一种本身就是很强且简单的工程基线，不能只跟“给所有key全局放行”的弱方案比较。

如果局部投影与普通schema-aware基线结果相同，应接受“标准方法已经解决这个子问题”，而不是再加一层Agent宣称创新。旧120最多用于开发回放；新增来源信息带来的收益，应称为输入/系统设计收益，不能宣称同输入下语义分类算法更优。

建议的后续验收仅先测：证据是否真实可得、static/dynamic来源是否绑定正确、非证据区间遮罩是否保持、正标签是否保持、detect/prepare是否一致。没有这些生产证据时，停止自动排除这条路线，保留当前默认。

## 6. 最近邻核查：已有能力与差别

本轮只核对直接相关的一手项目资料，未安装、下载或运行作者代码。

- Presidio Analyzer已经为识别结果附加recognizer身份，并按识别器组织上下文处理；其allow_list支持exact/regex文本匹配。说明“多识别器＋上下文＋可追踪来源”不是空白；全局文字allowlist也不等价于本项目要求的逐来源、逐位置、正约束优先处理。[官方Analyzer源码](https://github.com/data-privacy-stack/presidio/blob/main/presidio-analyzer/presidio_analyzer/analyzer_engine.py)
- Presidio Structured的JsonAnalysisBuilder将JSON分析结果映射到字段路径，PandasAnalysisBuilder按列分析值。结构化字段输入和按字段组织检测已经有成熟实现，不能把改成JSON或只扫描列值当作新算法。这里需要额外验证动态key、受签名保护的片段及跨记忆传播是否仍保留。[官方Structured源码](https://github.com/data-privacy-stack/presidio/blob/main/presidio-structured/presidio_structured/analysis_builder.py)
- Presidio官方文档也已有可定制上下文增强及多种NER引擎。这不足以证明它适合本项目的中文业务名称，更不能据此推断其在旧120上的成绩；本轮没有运行该比较。[官方Analyzer文档](https://microsoft.github.io/presidio/analyzer/)

上述对照支持将本提议定位为受约束的工程强基线，而不是“无人做过”的论文贡献。真正尚待证明的部分，是生产来源证据能否在记忆生成、迁移和prepare中持续保持，并在强基线、独立新材料与合法回答效用上产生可重复的价值。本轮没有这些效果结果。

## 7. 在原输入约束内，下一项实证应换什么

在不增加生产renderer来源的原payload/policy条件下，下一项合理实证是更强的多语言本地实体/关系提取基线，而不是继续给旧错例追加词表或换提示说法。本轮仅核对两张官方模型卡：现有`fastino/gliner2.5-multi-v1`的卡将其列为287M、mDeBERTa多语言检查点，具有实体和关系接口，但未提供中文分项结果；不能把当前失败归因为“必然只支持英语”，也不能将multilingual标签当成中文业务实体已验收。卡的当前载入示例为AutoExtractor；实际后续实验仍须对照本项目冻结revision和架构，不能据main卡变化断言历史运行器错配或直接升级。[GLiNER2.5官方模型卡](https://huggingface.co/fastino/gliner2.5-multi-v1)

8B容量对照可先考虑`Qwen/Qwen3-8B`：官方卡给出8.2B、多语言与关闭thinking的接口，它仍是通用生成模型，不是隐私/关系提取的效果保证。按参数估算，FP16仅权重约16.4GB，超过8GB显存；量化后能否连同上下文缓存运行，需要固定资产、运行时和预算后另行资格测试，不能只按“8B/4bit”宣布可行。优先使用完整原文、精确span和实体关系输出，分开评价候选覆盖、类型、关系、待审与费用；本轮未下载、推理或调参，也不声称换大模型本身是创新。[Qwen3-8B官方模型卡](https://huggingface.co/Qwen/Qwen3-8B)
