# WebUI 读取旁路：版本化判读合同

日期：2026-10-26。版本固定 **Open WebUI 0.12.3**。本轮仅源码复核，无 vendor 运行、原生请求、模型推理或 auth-state 读取；以下均为**冻结前的源码预期，不是实测成绩**。PUA 的证据驱动诊断应用于判读，不以空响应补安全成绩。

夹具前提：普通 owner 上传两个独立 `.txt`，`process=false`，各含19字节精确事实；每个文件挂在同一 owner 所建的独立 Note；四个组合主体通过不同普通原生用户认证。先确认同 ID 的 owner 原文读取阳性，再判断其他主体。不得改成 admin owner 或增加处理后的内容来补本轮阳性。

## 1. 七条路由不能共用一个内容成功标准

| 操作与固定请求 | 普通 owner 的源码预期 | 获 Note read 的非owner | 无相关授权的已认证非owner | 可计分证据及限制 |
|---|---|---|---|---|
| `file_metadata`：`GET /api/v1/files/{id}` | 200，原生 FileModel，至少以实际 file ID 建阳性；未处理 data 不应被要求含原文 | 通过 `has_access_to_file(...,'read')` 后可200，仍为同 file ID | 已存在 file 也返回404来隐藏存在性 | 可核metadata/ID隔离；不能要求原文值作为此接口的owner阳性 |
| `file_data_content`：`GET /files/{id}/data/content` | 200，`{"content":""}`：未处理文件没有索引正文 | 同样可200空content | 404 | 这是 processed-text 接口。空content符合本夹具语义，不是执行错误，也不构成秘密原值防护成功；状态/结构一致性与秘密载荷覆盖分开记 |
| `file_content_html`：`GET /files/{id}/content/html` | **预期404，本夹具标unsupported／不适用内容阳性**：ACL前要求 file 的所有者为admin，本夹具owner为普通user | 同样受前置条件阻断 | 同样404 | 不能将这些404算成已验证的read ACL拒绝。触发点是file owner角色，源码没有以“不是HTML”作该前置判定；不能改admin材料造阳性 |
| `file_content_named`：`GET /files/{id}/content/controlled.txt` | 原始文件存在时200 FileResponse，预期精确19字节，非JSON字符串 | Note read有效时可同样读原文 | 404 | 这是秘密载荷适用的路径。函数按id取file，未将URL后缀当磁盘路径或校验其等于原文件名；原件丢失时另有indexed text fallback，本夹具不能靠fallback补成绩 |
| `file_list`：`GET /files/?page=1&content=true` | 200 FileListResponse：`items`为文件对象数组、`total`为整数；应有两条自有file ID | **不能仅凭Note read枚举共享file**：路由以当前user.id筛所有权；本夹具非owner自有0，预期`items:[],total:0` | 同样自有0 | 空文件列表符合产品所有权视图，不等于源read拒答。`content=true`只保留已有file.data.content，不会处理/生成原文；本夹具不得因无值而计秘密安全成功 |
| `file_search`：`GET /files/search?filename=controlled_*&content=true&limit=100` | 200，匹配的自有文件对象JSON数组，预期两file ID | 路由仍按所有权；无自有匹配时404 | 同样404，原生detail为无匹配文件 | 这是SQL文件名搜索，不是全可读文件搜索或向量查询；404不能称为Note read的ACL拒绝，需与owner相同pattern阳性配对 |
| `note_search`：`GET /notes/search?query=controlled_&page=1` | 200 NoteListResponse；owner通常具有两个Note的write/read资格 | **默认查询语义为write**，只读共享主体可能200空items；不能当合法read缺失 | 预期无可见匹配Note | 见下节read变体。搜索响应会截短data，只保留content.md，不能要求file ID或原文阳性 |

上表均省略路径共同前缀 `/api/v1`。认证失败401、notes功能关闭、传输/存储异常和不合格owner阳性都须单列；不能把所有401/403/404统一计为权限防护成功。对于metadata、named-content、data/content，只有同对象owner阳性已建立且实际身份合格时，才可解释无权分支的隐藏性404。

FileModel/FileListResponse/NoteListResponse按实际原生schema验证，检查全items及注册ID，不以任意200空对象/null当作有效列表。本轮文件数2，小于文件页长50和limit100；Notes搜索page1的页长60，不能将这一小夹具的完整枚举结论推广到任意分页规模。

## 2. Note 搜索必须区分 write 与 read 两个变体

`routers/notes.py:170` 接受 `permission: Optional[str]`；传入时原样放入 `filter['permission']`，因此正式请求允许 `permission=read`，无需改vendor。

并行源码核验补充：`models/notes.py::search_notes` 第238—242行在未给permission时默认 **write**，第244—249行把选择交给 `_has_permission`；后者第157—165行调用 `AccessGrants.has_permission_filter(resource_type='note',permission=...)`。该模型文件SHA-256为 `31df0e16ad47e40b32e47fb673142ac89cb9fc9df39c84a8c65131bcf6a49888`；直接读取范围之外的这组行号来自并行只读核验者，不能冒称本轮独立逐行复核了全部model实现。

同一并行核验确认 `models/files.py` SHA-256为 `e0770c88528e5f95f64ee56fd11f1e662065ba269a7bf44688fa6d5ce224cb6d`：FileListResponse第100—102行为 `items:list[FileModelResponse],total:int`。metadata最少核对`id/user_id/filename`；其`data/meta/path`允许为None，不能因可空字段无原文误判执行失败。

冻结两种请求：

- **默认write对照**：原worker的 `note_search`。owner应有Note ID阳性；只有read的alice_reader可合理得到200空items。它不能作为共享read的效用或泄露主判据。
- **显式read主探针**：`GET /api/v1/notes/search?query=controlled_&page=1&permission=read`。预期保留当前owner/read grant允许的Note ID，撤销read后去掉相应ID，仍有独立合法read依据的Note应保留；G臂四主体未获原生ACL时不应枚举owner Note。最终匹配须用当时完整源读关系及实际原生ACL对照，不能从响应倒推参照。

两变体均执行 `_truncate_note_data`：响应data只剩 `{"content":{"md":...}}`，本夹具md为空，**data.files被去掉**。搜索应以Note ID作内容存在性阳性；file ID的关联通过另存的Note detail验证，原值读取通过正式content路径验证。即使空md，也不应忽略泄露的未授权Note ID。

## 3. 授权链与评分冻结规则

`utils/access_control/files.py` 的文件访问会汇总合法知识库、共享模型、channel、shared chat和file owner的共享Note；其中Note附件要求owner一致并精确匹配type=file及file ID。当前隔离夹具只建立已声明的Note/file，不能将可能存在的其他合法来源解释成漏洞；未来加入其他共享来源须重建授权参照。

建议每个响应分四轴保存：`transport/auth outcome`、`endpoint applicability`、`ID visibility`、`raw secret exposure`。先核真实普通身份与owner同接口阳性，再验证固定schema，最后按本路径的载荷语义评分；即使返回拒绝状态，只要正文仍有未授权原值/ID也必须记异常。未适用HTML、无原值的processed-content与ownership-only枚举不得加入秘密原值“防护通过”分母。

如果实际响应不符合上述版本化预期，保留失败原件并定位版本、对象、处理状态或模型过滤；不得改政策、材料、角色或私改评分公式凑通过。本轮新增read变体及额外owner/默认write配对属于计划，实际请求和最终qualification须由另存实验给出。
